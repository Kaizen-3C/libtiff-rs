# libtiff-rs

A memory-safe Rust port of the libtiff 4.7.0 **LZW decoder** — `LZWSetupDecode` +
`LZWPreDecode` + `LZWDecode` from `tif_lzw.c`, the code that decompresses LZW-encoded TIFF
strips/tiles. This is libtiff's richest untrusted-input codec surface: a 9–12-bit code-table
decoder whose bounds guards (code-table index limits, CLEAR/EOI handling, the "bogus input"
table-zeroing) are the classic LZW-overflow CVE territory.

The entire crate is **`#![forbid(unsafe_code)]`** and has **zero dependencies**.

## Scope

This crate is the **LZW decode path** — the highest-value codec in libtiff's compression set
and the one with the deepest untrusted-input attack surface. It is *not* all of libtiff. Out
of scope (and not in this crate): the TIFF directory/IFD parser, strip/tile plumbing, the
predictor, the LZW *encoder*, the backwards-compatible old-style LZW path (`LZWDecodeCompat`),
and the other codecs. The RLE-family codecs (PackBits, Thunder, NeXT) are separately certified
in the intent-engine campaign and are candidate additions to a future release; see the note at
the end. LZW is shipped first because it is the codec a hardened decoder most needs in Rust.

## Certification methodology

This port was not reviewed into correctness — it was **measured** into it. The upstream C
decoder and the Rust port are both driven by an identical op-script harness (`<occ> <hex>` per
stdin line: the requested output size and the raw LZW-compressed input) over a declared
envelope, and their complete observable stdout — decoder return code, decoded-byte hash, and
input-consumed count — is byte-compared against the upstream C build:

| Envelope | Cases | What it exercises | Result |
|---|---|---|---|
| `tests/vectors/tiff_*` | 261 | valid streams at exact/under/over output sizes; table-saturation / CLEAR regimes; every 9→10→11→12-bit code-width boundary (253–4096); the old-style-code rejection path; **plus** an adversarial half — truncation at every stage, single-byte bit-flips into "code not yet in table", missing EOI, and pure-garbage fuzz — with **153 of 261 exercising error/bounds paths** | **261/261 byte-identical** |

Valid streams are generated by a TIFF-LZW encoder verified to round-trip through the C decoder,
so the corpus is genuinely well-formed where it claims to be and genuinely hostile where it
claims to be. Run it yourself: `cargo test` replays the envelope through the crate's
`differential_driver` and compares against the checked-in golden; `scripts/regen_goldens.sh`
rebuilds the C reference from upstream and re-proves it (CI runs it every commit).

## How the port handles the C decoder's structure

`LZWDecode` in C is a `goto`-based state machine that walks a `code_t` linked-list code table
via raw pointers (including a one-before-the-array sentinel). The safe-Rust port reindexes
those pointer chains to array indices and restructures the `goto` machine into ordinary
control flow — with **zero `unsafe`** — while reproducing the C's exact accept/reject/bounds
behavior on every input in the envelope.

## API shape

A *safe-Rust* port: `lzw_decode(raw: &[u8], occ: usize) -> (ret, Vec<u8>, rawcc)` decodes an
LZW strip from a byte slice into an owned buffer, returning the C decoder's return code and
bytes-consumed count. Not ABI-compatible with C callers.

## Layout

- `src/lib.rs` — the LZW decoder
- `src/bin/differential_driver.rs` — the certification op-script driver (mirrors `cref/_driver.c`)
- `cref/` — the C reference harness: `_prelude.c` (minimal TIFF shim), `_driver.c` (op-script
  driver), `assemble.py` (slices the verbatim LZW decoder from an upstream `tif_lzw.c`)
- `tests/differential.rs` + `tests/vectors/` — full envelope replay
- `scripts/regen_goldens.sh` — download upstream, build the C reference, re-prove the differential

## Roadmap

The RLE codecs (PackBits, Thunder, NeXT) are separately certified against the same harness
methodology and are candidate additions. They are not bundled here because combining all four
decoders into one differentially-certified module in a single pass exceeded the porting
pipeline's reliable generation size; folding them in via per-codec modules is planned.
